# TinyLogLibrary 架构指导

## 0. 对齐原则

`LogLibraryOS.md` 是主参考文档，本文件只负责把它拆成适合 TinyLogLibrary 从 0 实现的阶段计划。

先固定一句话：

> Logger 管判断和分发，Recorder 表示一条日志，Sink 管写到哪里，Stylizer 管输出格式。

TinyLogLibrary 当前可以继续使用更直观的简化文件名，但概念要和 `LogLibraryOS.md` 对齐：

| LogLibraryOS 概念 | TinyLogLibrary 可用命名 | 职责 |
|---|---|---|
| `Recorder` | `LogRecord` | 保存一条日志的数据：内容、等级、时间、位置、logger 名称等 |
| `Stylizer` | `Formatter` / `Stylizer` | 把 `Recorder` 变成最终字符串 |
| `ISink` / `BaseSink` | `Sink` / `BaseSink` | 定义输出目标接口，并封装锁、格式化器等公共逻辑 |
| `Logger` | `Logger` | 等级判断、创建 Recorder、分发给多个 Sink |
| `Registry` | `Registry` | 管理默认 Logger、命名 Logger、全局等级、全局 flush 等 |

建议后续文档里优先使用 `Recorder`、`Stylizer` 这组概念名；如果代码文件继续叫 `LogRecord.h`、`Formatter.h`，要明确它们分别对应 `Recorder`、`Stylizer`。

---

## 1. 审查结论：原架构指导的偏离点

原文档总体方向没错，但和 `LogLibraryOS.md` 有几处明显偏离：

- **术语偏离**：原文把 `Recorder/Stylizer` 改成了 `LogRecord/Formatter`，但没有说明映射关系，容易和主文档断开。
- **主流程偏离**：`LogLibraryOS.md` 的主线是 `Logging.h -> Logger -> Recorder -> Sink -> Stylizer -> 输出`，原文没有把这条链路作为唯一主线。
- **异步位置偏离**：原文设计成 `AsyncSink`，而 `LogLibraryOS.md` 更接近 `AsyncLogger + ThreadPool + MPMCQueue`，异步属于 Logger/Registry 层面的高级能力，不应一开始包装成 Sink。
- **Sink 体系偏离**：主文档里有 `ISink`、`BaseSink`、`SinkIt()`、`Flush()`、`SetStylizer()`，原文只保留了简单 `Sink::Write()`，少了后续扩展点。
- **迭代顺序偏离**：`LogLibraryOS.md` 建议的顺序是“控制台日志 -> 文件日志 -> 日志等级 -> 文件名行号 -> 多 Sink -> 滚动日志 -> 多 Logger -> 异步日志”，原文把格式化、文件、多线程混在一起，阶段边界不够贴合。

所以本文件调整为：以 `LogLibraryOS.md` 的职责拆分和流程为准，但保留 TinyLogLibrary 从简到繁、每个阶段可编译可运行的实现方式。

## 2. 总体主流程

TinyLogLibrary 的最终主流程应该稳定成这样：

```plain
业务代码
    |
    | logging::Info("hello")
    v
Logging.h 入口函数
    |
    v
DefaultLoggerRaw()->Print(...)
    |
    v
Logger::Print()
    |
    v
ShouldLog(level)
    |
    |-- false：丢弃
    |
    |-- true
         |
         v
       Recorder / LogRecord
         |
         v
       Logger::LogItImpl()
         |
         v
       遍历所有 Sink
         |
         v
       Sink::SinkIt()
         |
         v
       Stylizer::Stylize()
         |
         v
       std::cout / std::cerr / log file
```

注意：`Sink` 决定“写到哪里”，`Stylizer` 决定“长什么样”。不要把格式化逻辑长期写死在 `ConsoleSink` 或 `FileSink` 里。

## 4. Phase 1：控制台日志最小闭环

**目标**：先跑通 `logging::Info("hello")` 到控制台输出。

这对应 `LogLibraryOS.md` 里的第一条主线：先理解业务怎么打日志，以及日志如何经过 `Logging.h -> Logger -> Recorder -> Sink -> Stylizer`。

### 二级拆分

| 子阶段 | 目标 | 完成标志 |
|---|---|---|
| 1.1 | 提供入口函数 | `logging::Info("hello")` 能调用默认 Logger |
| 1.2 | 创建最小 Recorder | `LogRecord` 至少保存 `level/message/time` |
| 1.3 | 输出到控制台 | `ConsoleSink::SinkIt(record)` 能把日志写到 `std::cout` |
| 1.4 | 接入最小 Stylizer | 控制台输出由 `Stylizer/Formatter` 生成，而不是完全写死在 Sink 里 |

### 产出文件

```plain
tiny_log/
  LogLevel.h
  LogRecord.h
  Sink.h
  Stylizer.h 或 Formatter.h
  ConsoleSink.h
  Logger.h
  Logger.cpp
  Logging.h
```

### 最小接口建议

```cpp
class Sink {
public:
    virtual ~Sink() = default;
    virtual void SinkIt(const LogRecord& record) = 0;
    virtual void Flush() = 0;
};
```

```cpp
class Stylizer {
public:
    virtual ~Stylizer() = default;
    virtual std::string Stylize(const LogRecord& record) = 0;
};
```

如果你决定继续使用 `Formatter` 这个名字，可以把接口写成 `Format()`，但文档中要说明它就是 `LogLibraryOS.md` 里的 `Stylizer`。

### 阶段验收

```cpp
logging::Info("hello world");
```

预期输出类似：

```plain
[Info] hello world
```

### 暂时不做

- 不做文件输出。
- 不做日志过滤。
- 不做源码位置。
- 不做多 Logger。
- 不做多线程。

## 5. Phase 2：文件日志和多 Sink

**目标**：一条日志可以同时写到控制台和文件。

这对应 `LogLibraryOS.md` 里的：`Logger` 持有 `std::vector<std::shared_ptr<ISink>>`，一个 Logger 可以分发到多个输出目标。

### 二级拆分

| 子阶段 | 目标 | 完成标志 |
|---|---|---|
| 2.1 | Logger 持有多个 Sink | `Logger::AddSink(...)` 后可以遍历所有 Sink |
| 2.2 | 实现普通文件输出 | `FileSink` 能追加写入、Flush、析构关闭 |
| 2.3 | 控制台 + 文件同时输出 | 一次 `logging::Info(...)` 能写入两个目标 |

### 新增/修改文件

```plain
tiny_log/
  FileSink.h          <- 普通文件输出
  Logger.h/.cpp       <- 增加 AddSink / ClearSinks / Flush
```

### 需要解决的问题

| # | 问题 | 方案 |
|---|---|---|
| 1 | Logger 如何输出到多个地方 | 内部保存 `std::vector<std::shared_ptr<Sink>>` |
| 2 | 文件打不开怎么办 | 构造 `FileSink` 时检查 `std::ofstream::is_open()` |
| 3 | 什么时候 Flush | 先提供手动 `Logger::Flush()`，自动 flush 留到后面 |

### FileSink 最小接口建议

```cpp
class FileSink : public Sink {
public:
    explicit FileSink(const std::string& filename, bool append = true);
    void SinkIt(const LogRecord& record) override;
    void Flush() override;

private:
    std::ofstream file_;
};
```

### 阶段验收

```cpp
auto logger = logging::DefaultLoggerRaw();
logger->AddSink(std::make_shared<ConsoleSink>());
logger->AddSink(std::make_shared<FileSink>("app.log"));

logging::Info("app started");
```

控制台和 `app.log` 都能看到日志。

## 6. Phase 3：日志等级和过滤

**目标**：Logger 能根据等级决定是否输出。

这对应 `LogLibraryOS.md` 中 `Logger::ShouldLog(level)` 的职责。

### 二级拆分

| 子阶段 | 目标 | 完成标志 |
|---|---|---|
| 3.1 | 完善 LogLevel | 支持 `Trace/Debug/Info/Warn/Error/Critical/Off` |
| 3.2 | Logger 保存当前等级 | `SetLevel()` / `GetLevel()` 可用 |
| 3.3 | 实现 ShouldLog | 低于当前等级的日志不会进入 Sink |

### LogLevel 建议

```cpp
enum class LogLevel {
    Trace,
    Debug,
    Info,
    Warn,
    Error,
    Critical,
    Off
};
```

### 阶段验收

```cpp
logger->SetLevel(LogLevel::Warn);

logging::Info("not printed");
logging::Error("printed");
```

只有 Error 输出。

### 说明

后续进入多线程阶段后，`Logger` 的等级可以改成 `std::atomic<int>`，对齐 `LogLibraryOS.md` 中的线程安全设计。

## 7. Phase 4：源码位置和完整 Recorder

这对应 `LogLibraryOS.md` 中 Recorder 保存的内容：payload、level、logger_name、time_point、file/function/line、thread id 等。

### 二级拆分

| 4.2 | 扩展 LogRecord 字段 | 至少包含 `logger_name/time/file/function/line` |
| 4.3 | 入口宏捕获位置 | `LOGGING_INFO("x")` 或 `LOG_INFO("x")` 能显示调用位置 |

### 新增/修改文件

```plain
tiny_log/
  SourceLocation.h
  LogRecord.h
  Logging.h
```

### SourceLocation 建议

```cpp
struct SourceLocation {
    const char* file;
    const char* function;
    int line;

```

```cpp
    tiny_log::SourceLocation{__FILE__, __func__, __LINE__}
```

### 阶段验收

## 8. Phase 5：Stylizer 格式化体系

**目标**：把“日志长什么样”从 Sink 中彻底抽出来。

这对应 `LogLibraryOS.md` 的 `Stylizer::Stylize()`。`Sink` 只负责写目标，`Stylizer` 负责生成字符串。

### 二级拆分

| 子阶段 | 目标 | 完成标志 |
|---|---|---|
| 5.1 | 定义 Stylizer 接口 | `Stylize(record)` 返回最终字符串 |
| 5.2 | Sink 持有 Stylizer | `ConsoleSink/FileSink` 都通过 Stylizer 生成文本 |
| 5.3 | 支持不同格式 | 控制台简洁格式，文件完整格式 |

### 新增/修改文件

```plain
tiny_log/
  Stylizer.h 或 Formatter.h
  DefaultStylizer.h
  PatternStylizer.h      <- 可选，后续再做
  BaseSink.h
```

### 接口建议

```cpp
class Stylizer {
public:
    virtual ~Stylizer() = default;
    virtual std::string Stylize(const LogRecord& record) = 0;
    virtual std::unique_ptr<Stylizer> Clone() const = 0;
};
```

`Clone()` 是为了让多个 Sink 可以拥有各自独立的格式化器，对齐 `LogLibraryOS.md` 里 `std::unique_ptr<Stylizer>` 的所有权设计。

### BaseSink 建议

```cpp
class BaseSink : public Sink {
public:
    void SetStylizer(std::unique_ptr<Stylizer> stylizer);

protected:
    std::string Format(const LogRecord& record);

private:
    std::unique_ptr<Stylizer> stylizer_;
};
```

### 阶段验收

```plain
控制台：
[Info] app started

文件：
[2026-05-19 16:30:00] [default] [Info] [main.cpp:12 main] app started
```

## 9. Phase 6：滚动日志和线程安全 Sink

**目标**：文件不会无限增大，多线程写入不乱。

这对应 `LogLibraryOS.md` 中的 `BaseSink<Mutex>`、`NullMutex`、`RotatingFileSink`。

### 二级拆分

| 子阶段 | 目标 | 完成标志 |
|---|---|---|
| 6.1 | 抽出 BaseSink 模板 | `BaseSink<std::mutex>` 和 `BaseSink<NullMutex>` 复用一套逻辑 |
| 6.2 | 实现 RotatingFileSink | 超过 max_size 后轮转文件 |
| 6.3 | 提供 ST/MT 两种别名 | 单线程版无锁，多线程版加锁 |

### 新增/修改文件

```plain
tiny_log/
  BaseSink.h
  RotatingFileSink.h
  detail/
    NullMutex.h
```

### 轮转策略

```plain
app.log   -> app.1.log
app.1.log -> app.2.log
app.2.log -> app.3.log
超过保留数量后删除最旧文件
```

### 接口建议

```cpp
template<typename Mutex>
class BaseSink : public Sink {
public:
    void SinkIt(const LogRecord& record) final {
        std::lock_guard<Mutex> lock(mutex_);
        SinkItImpl(record);
    }

protected:
    virtual void SinkItImpl(const LogRecord& record) = 0;

private:
    Mutex mutex_;
};
```

### 类型别名建议

```cpp
using RotatingFileSinkST = RotatingFileSink<detail::NullMutex>;
using RotatingFileSinkMT = RotatingFileSink<std::mutex>;
```

## 11. Phase 8：异步日志

**目标**：业务线程不直接执行慢 IO。

这里要和 `LogLibraryOS.md` 对齐：优先理解为 `AsyncLogger + ThreadPool + Queue`，而不是把异步强行塞进 `AsyncSink`。

### 二级拆分

| 子阶段 | 目标 | 完成标志 |
|---|---|---|
| 8.1 | 实现阻塞队列版本 | 业务线程入队，后台线程出队并分发到 Sink |
| 8.2 | 抽出 AsyncLogger | `AsyncLogger::Print()` 只负责创建 Recorder 并提交任务 |
| 8.3 | 再优化队列 | 功能稳定后再考虑 MPMCQueue / RingBuffer |

### 新增/修改文件

```plain
tiny_log/
  AsyncLogger.h
  detail/
    ThreadPool.h
    BlockingQueue.h      <- 第一版推荐
    MPMCQueue.h          <- 后续优化，对齐 LogLibraryOS
```

### 简化流程

```plain
业务线程
  |
  | logging::Info(...)
  v
AsyncLogger::Print()
  |
  | 创建 Recorder 并入队
  v
Queue
  |
  | 后台线程取出
  v
Logger::LogItImpl()
  |
  v
Sink::SinkIt() -> Stylizer::Stylize() -> 输出
```

### 暂时不做

- 不做 crash 时强制兜底落盘。
- 不一开始实现无锁队列。
- 不把所有 Sink 都改成异步 Sink。

## 12. Phase 9：应用层初始化和可选高级特性

**目标**：学习 `LoggerManager` 的思想，但不要把应用层逻辑写死进日志库。

`LogLibraryOS.md` 里的 `LoggerManager` 是应用层配置，不是底层日志库必需组成部分。TinyLogLibrary 可以提供示例或辅助函数，但核心库保持通用。

### 二级拆分

| 子阶段 | 方向 | 可选特性 |
|---|---|---|
| 9.1 | 应用初始化示例 | 创建默认 logger、添加控制台 sink、添加滚动文件 sink |
| 9.2 | 运行时配置 | 环境变量控制 quiet mode、默认 level、日志目录 |
| 9.3 | 易用性增强 | fmt 支持、流式入口、条件日志、CallbackSink、ColorSink |

### 可选特性列表

- `fmt` 支持：`logging::Info("x={}", x)`。
- 流式入口：`LOGGING_INFO << "x=" << x`。
- 条件日志：`LOGGING_INFO_IF(cond, "message")`。
- `CallbackSink`：把日志交给用户回调。
- `ColorSink`：按等级输出颜色。
- `PeriodicWorker`：定时 Flush。
- 环境变量：例如 `TINY_LOG_QUIET=1`、`TINY_LOG_LEVEL=Debug`。

## 13. 推荐迭代顺序总览

这版顺序严格贴近 `LogLibraryOS.md` 的建议：

```plain
Phase 0  工程结构和命名对齐
   |
Phase 1  控制台日志最小闭环
   |
Phase 2  文件日志和多 Sink
   |
Phase 3  日志等级和过滤
   |
Phase 4  源码位置和完整 Recorder
   |
Phase 5  Stylizer 格式化体系
   |
Phase 6  滚动日志和线程安全 Sink
   |
Phase 7  多 Logger 和 Registry
   |
Phase 8  异步日志
   |
Phase 9  应用层初始化和高级特性
```

核心原则：

- 每个 Phase 都必须可编译、可运行。
- 每次只解决一个设计问题。
- 始终保持主流程不变：`Logging.h -> Logger -> Recorder -> Sink -> Stylizer -> 输出`。
- 底层库只做通用能力，应用层配置放到示例或 `LoggerManager` 风格的单独模块里。
